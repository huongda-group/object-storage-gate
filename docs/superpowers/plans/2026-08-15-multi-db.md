# Multi-DB (Postgres / MySQL / SQLite) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Chạy được production trên cả Postgres, MySQL và SQLite — cùng một schema, cùng một test suite, cả ba đều xanh trong CI.

**Architecture:** Thêm driver `sqlx-mysql` vào SeaORM; đổi ba câu SQL thô trong migration sang `SchemaManager` (chỗ nào không portable được thì branch theo `DatabaseBackend`); nuốt đúng một lỗi `reset_autoincrement` của loco trên MySQL; chọn backend bằng `DB_TYPE` trong `.env` qua template Tera của config, `DATABASE_URL` vẫn override. Không đụng logic domain, không đổi schema, không sinh lại `_entities/`.

**Tech Stack:** Rust, loco-rs 0.16.4, SeaORM 1.1 (`sqlx-postgres` + `sqlx-sqlite` + `sqlx-mysql`), sea-orm-migration 1.1, Tera (config templating), GitHub Actions, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-08-15-multi-db-design.md`

## Global Constraints

- **MySQL tối thiểu 8.0.13** — functional index (`COALESCE(user_id, 0)`) không có ở bản thấp hơn. Docker image pin `mysql:8`.
- **Không sinh lại `src/models/_entities/`.** Thư mục đó là output của `cargo loco db entities` chạy trên Postgres và là canonical. Chạy lại trên MySQL/SQLite sẽ ra kiểu dữ liệu khác và làm hỏng model.
- **Không đụng schema, không sửa migration cũ về mặt cột.** Chỉ đổi cách *tạo index*, không đổi index nào tồn tại.
- **SQL portable:** cấm `ILIKE`, `RETURNING`, `ON CONFLICT` / `ON DUPLICATE KEY`, `jsonb`, array column, `pg_advisory_lock`, `SELECT ... FOR UPDATE SKIP LOCKED`.
- **Không commit thay người dùng ngoài các bước `git commit` đã ghi rõ trong plan này.** (Repo `CLAUDE.md` cấm auto-commit; các step commit dưới đây là chỉ dẫn tường minh nên được phép.)
- **Không thêm dependency mới.** Chỉ bật thêm feature của crate đã có.
- Sau mỗi task: `cargo fmt` và `cargo clippy --all-targets` phải sạch (CI chạy với `-D warnings -W clippy::pedantic -W clippy::nursery`).

- [ ] **Step 2: Sửa `m20260724_000006_objects.rs` — bỏ SQL thô, dùng `SchemaManager`**

Thay toàn bộ nội dung file bằng:

```rust
use loco_rs::schema::*;
use sea_orm_migration::prelude::*;

const IDX_OBJECTS_BUCKET_KEY: &str = "idx_objects_bucket_key";

#[derive(DeriveMigrationName)]
pub struct Migration;

#[async_trait::async_trait]
impl MigrationTrait for Migration {
    async fn up(&self, m: &SchemaManager) -> Result<(), DbErr> {
        create_table(
            m,
            "objects",
            &[
                ("id", ColType::PkAuto),
                ("pid", ColType::UuidUniq),
                ("object_key", ColType::String),
                ("size", ColType::BigIntegerWithDefault(0)),
                ("etag", ColType::StringWithDefault(String::new())),
                (
                    "content_type",
                    ColType::StringWithDefault("application/octet-stream".to_string()),
                ),
            ],
            &[("buckets", "")],
        )
        .await?;
        // `has_index` thay cho `IF NOT EXISTS`: MySQL không có cú pháp đó cho index.
        if !m.has_index("objects", IDX_OBJECTS_BUCKET_KEY).await? {
            m.create_index(
                Index::create()
                    .name(IDX_OBJECTS_BUCKET_KEY)
                    .table(Alias::new("objects"))
                    .col(Alias::new("bucket_id"))
                    .col(Alias::new("object_key"))
                    .unique()
                    .to_owned(),
            )
            .await?;
        }
        Ok(())
    }

    async fn down(&self, m: &SchemaManager) -> Result<(), DbErr> {
        drop_table(m, "objects").await?;
        Ok(())
    }
}
```

Lưu ý: `use sea_orm_migration::sea_orm::ConnectionTrait;` bị bỏ đi vì không còn `execute_unprepared` — để lại sẽ thành warning `unused import` và clippy đánh rớt.

```rust
            let sql = match m.get_database_backend() {
                DatabaseBackend::MySql => format!(
                    "CREATE UNIQUE INDEX {IDX_BUCKETS_OWNER_NAME} \
                     ON buckets ((COALESCE(user_id, 0)), name)"
                ),
                _ => format!(
                    "CREATE UNIQUE INDEX {IDX_BUCKETS_OWNER_NAME} \
                     ON buckets (COALESCE(user_id, 0), name)"
                ),
            };
            m.get_connection().execute_unprepared(&sql).await?;
        }
```

### Task 3: Seed chạy được trên MySQL

**Files:**
- Modify: `src/app.rs:88-93` (hàm `seed`)
- Test: `tests/models/users.rs` (thêm một test mới ở cuối file)

**Interfaces:**
- Consumes: từ Task 2 — migrate chạy sạch trên MySQL.
- Produces: `App::seed` trả `Ok(())` trên cả ba backend. Mọi test gọi `seed::<App>(&boot.app_context)` dùng được trên MySQL.

**Bối cảnh cho người thực hiện:** `loco_rs::db::seed` (`db.rs:279`) insert xong hết các dòng trong YAML rồi mới gọi `reset_autoincrement`, và hàm đó trả `Error::Message("Unsupported database backend: MySQL")` (`db.rs:410`). Nghĩa là dữ liệu đã vào DB đúng, chỉ có bước cuối chết. Trên MySQL bước đó thừa thật: InnoDB tự đẩy bộ đếm `AUTO_INCREMENT` lên khi insert id tường minh, nên sau khi seed 2 dòng id 1–2 thì id kế tiếp đã là 3. Postgres và SQLite thì cần bước reset đó (sequence không tự nhảy) nên không được đụng vào nhánh của chúng.

Trong `src/app.rs`, thay hàm `seed` bằng:

```rust
    async fn seed(ctx: &AppContext, base: &Path) -> Result<()> {
        let path = base.join("users.yaml").display().to_string();
        // ponytail: loco's db::seed ends with reset_autoincrement, which hard-errors
        // on MySQL — but it fires only after every row is already inserted, and
        // InnoDB advances the AUTO_INCREMENT counter on explicit-id inserts by
        // itself, so nothing is left undone. Swallow that one error, nothing else.
        // Upgrade path: patch loco upstream to no-op there instead of erroring.
        match db::seed::<users::ActiveModel>(&ctx.db, &path).await {
            Err(Error::Message(msg)) if msg.contains("Unsupported database backend: MySQL") => {
                Ok(())
            }
            other => other,
        }
    }
```

`Error` đã có sẵn trong `use loco_rs::{...}` ở đầu file — không cần thêm import.

**Đây là điểm rủi ro lớn nhất của cả plan.** Nếu MySQL fail ở chỗ timestamp (`DateTimeWithTimeZone` ↔ `TIMESTAMP` không mang timezone) hoặc `pid` (`Uuid` ↔ `binary(16)`), **dừng lại, đừng tự chữa cháy** — báo lại kèm log lỗi. Phương án dự phòng đã ghi ở §3.5 của spec (đổi sang timestamp naive UTC bằng một migration mới) là quyết định cần người duyệt, không phải việc làm lén trong task này.

Nếu fail chỉ ở snapshot `insta` do format timestamp khác nhau: thêm filter vào `configure_insta!` của file test đó (`tests/models/users.rs` đã có sẵn cơ chế `cleanup_user_model()`), **không** tách snapshot theo backend.

- [ ] **Step 1: Thêm ràng buộc portable SQL vào `CLAUDE.md`**

Thêm vào mục **Constraints that bite** của `CLAUDE.md`:

```markdown
- **Ba backend ngang hàng: Postgres, MySQL (>= 8.0.13), SQLite.** Mọi SQL viết mới phải chạy được cả ba. Cấm `ILIKE`, `RETURNING`, `ON CONFLICT` / `ON DUPLICATE KEY`, `jsonb`, array column, `pg_advisory_lock`, `SELECT ... FOR UPDATE SKIP LOCKED`. Migration dùng `ColType` + `SchemaManager` trước; SQL thô chỉ khi bắt buộc (index functional) và phải branch theo `m.get_database_backend()` — xem `migration/src/m20260724_000002_buckets.rs`.
- **Quota mutation không dùng lock.** `reserve`/`commit`/`release` là một câu `UPDATE ... WHERE <guard>` rồi đọc `rows_affected` — atomic trên cả ba backend. Advisory lock chỉ có ở Postgres nên không xài được.
- **SQLite chỉ một writer.** Đường ghi phải chịu được `SQLITE_BUSY`; `busy_timeout=5000` + WAL do `loco_rs::db::connect` tự set, không phải cấu hình lại.
- **`src/models/_entities/` chỉ sinh từ Postgres.** `cargo loco db entities` chạy trên MySQL/SQLite sẽ ra kiểu dữ liệu khác và làm hỏng model.
- **loco chưa có `bg_mysql`.** Nếu đổi `workers.mode` sang `BackgroundQueue` thì MySQL bắt buộc dùng Redis queue.
- **Vài lệnh CLI loco không chạy trên MySQL:** `db dump`/`dump_schema` (`loco_rs::db::get_tables`) và `reset_autoincrement`. Cái sau đã được `App::seed` xử lý; cái trước thì dùng Postgres/SQLite mà dump.
```
